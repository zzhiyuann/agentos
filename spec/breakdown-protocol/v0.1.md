# Breakdown Protocol — v0.1 Specification

**Status:** Frozen v0.1 (2026-05-03). First specification freeze; intended to unblock external adapter work.
**Lineage:** RYA-733 / RYA-745 (proposal), RYA-768 (initial draft), RYA-770 (taxonomy validation), RYA-769 (this freeze).
**Authors:** Research Lead, with technical conditions from CTO and structural draft from Lead Engineer.
**Layered over:** OpenTelemetry GenAI semantic conventions, W3C Trace Context, MCP, A2A.

---

## 0. What this document is — and is not

**Is.** A specification for a typed runtime signal that agent orchestrators use to detect *pragmatic* conversational failure (failure that does not throw an exception) and inject a structured *repair turn* in response. It defines (a) the breakdown taxonomy, (b) the repair-turn payload schema, and (c) the W3C-trace-compatible attribute schema for observability.

**Is not.** A detector. The Protocol does not specify *how* a breakdown is identified — that is a classifier concern (rules, judge-LLM, fine-tuned model, hybrid). The Protocol specifies the *interface* between detector and orchestrator, and between orchestrator and agent.

**Is not.** A guardrail or eval framework. Those are *prevention* tools that run before or alongside the agent. Breakdown Protocol is *post-failure repair* — it activates when something has gone wrong that prevention did not catch. Prevention filters the boundaries; repair watches the loop in the middle.

---

## 1. Taxonomy

A breakdown is a pragmatic agent failure: the agent has not thrown an exception, but the session has stopped making progress against the user's intent OR is about to make negative progress. v0.1 defines two layers.

### 1.0 Two-layer taxonomy

| Layer | Categories | Repair path |
|---|---|---|
| **Cognitive** (§1.1–1.5) | `drift`, `ambiguity`, `dead_loop`, `misalignment`, `context_collapse` | Repair-turn injection (§2) |
| **Substrate** (§1.6–1.7) | `infrastructure_failure`, `tool_error` | Halt + substrate fix; NOT repair-turn (§4.4) |

**Why two layers (load-bearing).** The 30-day AgentOS retrospective corpus (RYA-770, n=104 incidents) shows that 32% of operational pain is substrate-level (auth expired, env var missing, tool silently lying, concurrent-session file race), not cognitive. Routing substrate failures to a repair-turn class produces *repair-turn storms* — the exact failure mode the Protocol exists to prevent. Substrate signals exist as peers, not as a sixth cognitive category, because their repair primitive is fundamentally different (orchestrator halts the agent and fixes the substrate; it does not negotiate with the agent).

**Mutual exclusivity at detect time.** A single detection emits exactly one type. A session MAY experience multiple breakdowns serially. When a classifier sees signals for multiple types simultaneously, it MUST pick the type with the highest evidence weight and emit one event, with secondary candidates listed in `evidence.alternatives`. Tie-break order: substrate signals beat cognitive (a failing tool is not a drifting agent); within cognitive, apply observable rules in §1.8.

### 1.1 `drift` (cognitive)

**Definition.** The agent is making forward progress, but the *direction* of that progress has diverged from the stated user intent. Work is being done; it is being done wrong.

**Operational signature (any one is sufficient evidence):**
- The agent has executed ≥ 3 tool calls before producing or modifying any artifact named in the user's request.
- Successive plans across turns *N* and *N+k* contradict each other on scope, deliverable, or success criterion.
- The agent's running task description (self-stated or derived from recent tool calls) has diverged measurably from the user-stated goal (cosine-similarity drop, scope inflation ratio above threshold, or rule-based scope-compare).
- The agent has produced ≥ *T* consecutive turns of work that do not advance any artifact named in the user's request.

**Disambiguation:**
- *Not `misalignment`*: drift is observed as ≥ 3 tool calls before user-named artifact. Misalignment is observed as a produced artifact answering a different question than asked.
- *Not `context_collapse`*: drift is direction of progress. Context_collapse is fidelity to established state.
- *Not `infrastructure_failure`*: drift requires the agent to be live and making forward progress.
- *Not an exception*: nothing threw.

**Default repair directive class:** `reorient`.

**Illustrative incidents (from AgentOS corpus):**
- Agent given narrow ops scope writes a strategy doc instead.
- "Should have run full-dataset validation before 28 experiments to reveal ceiling earlier" (RYA-254 retro): agent ran 28 experiments before validating ceiling — observed as ≥ 3 tool calls before artifact validation.
- Agent told to fix a bug, ends up refactoring nearby code.

### 1.2 `ambiguity` (cognitive)

**Definition.** The user request is underspecified along a dimension that materially affects the answer, and the agent is proceeding past that ambiguity without acknowledging it or resolving it — OR the agent has stopped to ask successive clarifying questions without progress.

**Operational signature:**
- The agent's *first action* on the turn was a clarification question, OR the agent has emitted ≥ 2 clarifying questions in a row without forward progress.
- The agent has made a plan-affecting choice (output format, target file, scope boundary, technical stack assumption) without quoting or paraphrasing the user's specification of that choice.
- A second-pass classifier identifies ≥ 2 plausible interpretations of the request, and the agent's path is consistent with only one.
- The agent's chain-of-thought (when available) names a parameter as "assumed" or "I'll go with" without prior user signal.

**Disambiguation:**
- *Not `misalignment`*: ambiguity is unresolved interpretation (the agent's first action was a question, or the agent guessed). Misalignment is a resolved-but-wrong target observable as a produced artifact.
- *Not `drift`*: ambiguity manifests at turn one (first action). Drift manifests after ≥ 3 tool calls.
- *Not a parse error*: the request is well-formed but polysemic.

**Default repair directive class:** `clarify` — surface the question to the user (or higher-priority agent in a hierarchy) before continuing.

**Illustrative incidents:**
- Prompt missing required field; agent asks user 3+ questions before any progress.
- Description vs comments contain conflicting instructions; agent proceeds against one without flagging.

### 1.3 `dead_loop` (cognitive)

**Definition.** The agent — or the system on the agent's behalf — is repeating the same action, or trivially perturbed variants of the same action, without converging on progress. The retry pattern is itself the failure mode.

**Two operational sub-types** (RYA-770 edit 1 — both share the `dead_loop` parent, different runtime gates):

**1.3.a `dead_loop.in_session` — within one agent turn-loop.**
- The same tool name appears ≥ *T* times in the last *W* turns with arguments that match by exact equality OR after normalization (whitespace, case, key-order, retry-token stripping).
- No artifact named in the user's request has advanced over the same window.
- Chain-of-thought (if present) shows repeated reasoning patterns ("let me try again", "perhaps if I", "let me try once more") without changing the underlying approach.
- **Repair primitive:** repair-turn injection (`break_loop` directive, §2.4).

**1.3.b `dead_loop.cross_session` — system-level loop across sessions.**
- The orchestrator scheduler/heartbeat re-spawns the same task target ≥ *N* times within window *W*, with no terminal state advance.
- Substring/dedup match on the dispatch target fails (zombie proactive respawn, idle-false-complete + redispatch).
- **Repair primitive:** orchestrator-side back-pressure gate, NOT a repair-turn (the agent has no turn yet). Detection emits `breakdown.detect` with type `dead_loop.cross_session`; the gate is enforced at dispatch, not by injecting a repair turn into a non-existent conversation.

**Disambiguation:**
- *Not an exception*: the underlying tool may be returning errors, but the agent is *catching* them and retrying without strategy change.
- *Not `drift`*: dead_loop is stuck in place. Drift is moving in the wrong direction.
- *Not `infrastructure_failure`*: a loop *driven by* upstream rate-limit/auth is `infrastructure_failure` (the loop will not resolve until substrate is fixed). Tie-break: substrate signal wins.
- *Not infrastructure retry*: a well-formed exponential backoff with a finite cap is not a dead_loop. The signature is unbounded retry without strategy change.

**Default repair directive class:** `break_loop` (in_session); orchestrator gate (cross_session — no repair-turn).

**Illustrative incidents:**
- Zombie [proactive] respawn loop (RYA-665/698) — `cross_session`.
- Idle-detection false-completion + immediate re-dispatch (RYA-204/206) — `cross_session`.
- Substring matching on identifiers caused duplicate spawn loop (RYA-698) — `cross_session`.
- Agent retries the same failing tool call without varying inputs — `in_session`.

### 1.4 `misalignment` (cognitive)

**Definition.** The agent's output has diverged from intent — wrong file, wrong scope, wrong interpretation — even when the prompt was clear. The agent is optimizing a proxy metric the user did not ask for.

**Operational signature:**
- The agent has *produced* an artifact (file, message, decision, output), and the artifact answers a different question than asked.
- The output satisfies the literal request while violating an expressed-but-not-formalized constraint (user said "quick check"; agent produced a 2,000-word report).
- A second-pass classifier judges that the next stated step would *increase* a quality metric the user did not name *and* not advance any user-named criterion.
- The agent has self-imposed a quality criterion (length, completeness, exhaustiveness, breadth, citation count) that does not appear in the user's request and is being optimized at the expense of stated criteria.

**Disambiguation:**
- *Not `drift`*: drift is observable as ≥ 3 tool calls before user-named artifact, mid-flight. Misalignment is observable in a *produced* artifact that answers the wrong question.
- *Not `ambiguity`*: ambiguity is unresolved interpretation observable at turn one. Misalignment is a resolved-but-wrong target observable in output.
- *Not a guardrail violation*: the output passes guardrails. It is well-crafted work for the wrong question.

**Default repair directive class:** `realign`.

**Illustrative incidents:**
- Edits in the wrong repo.
- Misinterprets a `[to decide]` sub-issue as work to do.
- Closes an issue with open recommendations.

### 1.5 `context_collapse` (cognitive)

**Definition.** The agent has lost, contradicted, or is operating against an out-of-date version of state established earlier in the session OR established in durable substrate (workspace, memory, state files). State includes user-stated constraints, named entities, prior decisions, verified facts, tool-call results, and prior-session artifacts the current session depends on.

**Three operational sub-types** (RYA-770 edit 2 — substrate state loss is the dominant real-world variant, 12/22 of corpus context_collapse incidents):

**1.5.a Within-conversation memory loss.**
- The agent contradicts a constraint the user previously stated (e.g., "use Python" → agent writes Go).
- The agent re-asks for information the user already provided in a prior turn.
- A summarization or context-compaction step has occurred and the agent's subsequent turns do not reflect the pre-compaction state.

**1.5.b Substrate state loss (workspace/state-file).**
- A concurrent agent session, hook, or auto-deploy has clobbered the workspace state mid-session.
- The agent's prior tool result cannot be reconstructed from durable artifacts because the artifact was overwritten.
- A `state.json` / `HANDOFF.md` mismatch with the agent's in-memory model.

**1.5.c Stale durable state across sessions.**
- The agent reads `memory.md` / `state.json` written under a prior schema, makes assumptions inconsistent with current schema.
- A fresh session is unaware of an earlier session's HANDOFF that materially changes the task.

**Disambiguation:**
- *Not `drift`*: drift is direction of progress; context_collapse is fidelity to established state.
- *Not `dead_loop`*: dead_loop repeats actions; context_collapse forgets that actions were taken.
- *Not `ambiguity`*: ambiguity is the user underspecifying; context_collapse is the agent losing what *was* specified.
- *Not `infrastructure_failure`*: 1.5.b can co-occur with substrate failure. Tie-break: if the workspace was clobbered by a substrate process and the agent is dead at substrate level, classify as `infrastructure_failure`. If the agent is live but the state it reads is stale, classify as `context_collapse`.

**Default repair directive class:** `reground` — re-inject canonical state (from durable storage: HANDOFF.md, prior tool results, stated constraints) and require the plan to be re-derived from that state.

**Illustrative incidents:**
- Concurrent agent file race: two agent sessions edit the same file → one overwrites the other (1.5.b).
- Stale memory.md after schema change (1.5.c).
- Cross-session: fresh agent unaware of prior HANDOFF (1.5.c).
- Long-running session pre-compaction confuses two parallel tasks (1.5.a).

### 1.6 `infrastructure_failure` (substrate, peer signal)

**Definition.** Pre-conversation or substrate-level failure that prevents the agent from making any cognitive progress. The agent is dead, freezing, or running on broken substrate. **22.1% of the AgentOS corpus.**

**Operational signature (any one is sufficient evidence):**
- OAuth / API token expired before or during the session, with no in-loop refresh path.
- Required environment variable missing (`AOS_LINEAR_TEAM_ID`, etc.).
- Network/transport-level failure (rate-limit-at-startup, tunnel down, host unreachable).
- Filesystem watcher / OS-level subsystem failure (`fs.watch` recursive on Linux, etc.).
- The session never produced a turn, OR the session produced one turn and then froze on a substrate-level prompt (interactive auth, etc.).

**Disambiguation:**
- *Not a cognitive breakdown.* The agent has not made a cognitive error. The substrate has failed.
- *Not `dead_loop`*: a loop *driven by* infrastructure failure (e.g., 100+ failed retries due to rate-limit) MUST classify as `infrastructure_failure`, not `dead_loop`. Tie-break: substrate signal wins.
- *Not `context_collapse`*: substrate-level concurrent-session clobbering is `context_collapse.substrate_state_loss` (§1.5.b) IF the agent is live. If the substrate failure killed the agent or never let it start, it is `infrastructure_failure`.

**Default repair path:** **Halt + substrate fix + retry.** This routes to a different orchestrator path than cognitive breakdowns. The orchestrator MUST NOT inject a repair-turn for `infrastructure_failure`. See §4.4.

**Illustrative incidents:**
- OAuth token expired at startup (RYA-591).
- Rate-limit-at-startup interactive prompt (RYA-601).
- `linear-tool` token expired mid-session, agent could not post completion comment (RYA-254).
- Missing env var blocks dispatch (recurrent across CPO/COO/CTO retros).

### 1.7 `tool_error` (substrate, peer signal)

**Definition.** A tool returned wrong, silent, or empty output that breaks the agent's mental model of system state. **9.6% of the AgentOS corpus.**

**Operational signature:**
- The tool returned a 200/success code but the response payload is empty, malformed, or semantically inconsistent with the documented contract.
- The tool returned silently (no error, no result) and the agent's plan implied a non-empty result.
- Shell-escaping or argument-passing bugs in a wrapping CLI (e.g., `linear-tool` with parens/apostrophes).
- A subprocess conflict (`claude -p` concurrent sessions) produced wrong output.

**Disambiguation:**
- *Not `infrastructure_failure`*: the tool is reachable and responded. The response is wrong.
- *Not `context_collapse`*: from the agent's perspective, a silently-lying tool can *look* like context_collapse (state diverged from reality). Tie-break: if a tool's output is the proximate cause of the agent's wrong state, classify as `tool_error`. The agent's repair primitive is "stop trusting this tool", not "rebuild context".
- *Not a tool exception*: an exception (4xx/5xx, parse error, schema violation) is handled by the existing tool-error layer.

**Default repair path:** **Halt + tool fix or skip.** Like `infrastructure_failure`, this routes to a substrate path, NOT a repair-turn. The orchestrator MAY emit a structured `dead_loop_suspected` warning to the agent if the tool is repeatedly failing in the same way, but does not inject a cognitive repair-turn. See §4.4.

**Illustrative incidents:**
- Python experiment runner failed silently on type coercion (RYA-254).
- `linear-tool` shell escaping bugs with parens/apostrophes (recurrent).
- Discord follow-up reply routing bug.
- GoEmotions label parsing edge case.

### 1.8 Tie-break order (observable, not causal)

When evidence supports multiple types, apply this priority order. Earlier categories pre-empt later ones.

1. **`infrastructure_failure`** if any substrate signature in §1.6 is met (substrate beats cognitive).
2. **`tool_error`** if any signature in §1.7 is met (substrate beats cognitive).
3. **`dead_loop.cross_session`** if scheduler/heartbeat repeats ≥ *N* times across sessions.
4. **`dead_loop.in_session`** if same tool ≥ *T* times within window with no progress.
5. **`context_collapse`** if state-loss signature in §1.5 is met (any sub-type).
6. **`ambiguity`** if first-action-was-clarification or ≥ 2 clarifications without progress.
7. **`misalignment`** if a produced artifact answers a different question than asked.
8. **`drift`** (residual cognitive) if ≥ 3 tool calls before user-named artifact.

This replaces causally-grounded definitions ("input was unclear" vs "agent misread") with log-observable ones, per RYA-770 edit 3.

### 1.9 Disambiguation vs. exception-style errors

The Protocol applies *only* to pragmatic and substrate-level failures detectable by reasoning over turns and state. The following are NOT breakdowns and MUST NOT be classified as such:

| Class | Signal | Where it's handled |
|---|---|---|
| Tool-call exception | HTTP 5xx, parse error, network timeout, API auth-during-call failure | Existing retry/fallback layer |
| Schema validation failure | Required field missing, enum mismatch | Validator layer (preventive) |
| Policy violation | Output triggered safety classifier | Guardrail layer (preventive) |
| Quota exhausted | Token budget, rate limit during normal operation | Quota / circuit breaker |
| Runtime crash | Process death, OOM, segfault | Process supervisor |

**Rule.** If `gen_ai.error.type` is set on the parent span, breakdown classification MUST be suppressed for that turn. (Note: `infrastructure_failure` per §1.6 is detected by *substrate* signals, not by `gen_ai.error.type` — the latter is used for in-call exception errors during normal operation.)

## 2. Repair-Turn Format

When a *cognitive* breakdown is detected, the orchestrator injects a repair turn into the agent conversation. Substrate signals (`infrastructure_failure`, `tool_error`) do NOT trigger a repair-turn — see §4.4.

The repair turn is a structured payload (JSON) wrapped in whatever transport the agent harness uses (system message, user message, tool result — implementation-defined).

### 2.1 Payload schema

```json
{
  "breakdown": {
    "type": "drift",
    "subtype": null,
    "detected_at": "2026-05-03T14:23:11.002Z",
    "confidence": 0.82,
    "evidence": {
      "summary": "Agent has produced 4 consecutive turns of refactor work; user requested a 1-line typo fix.",
      "turn_refs": ["msg_42", "msg_45", "msg_48", "msg_51"],
      "signals": [
        {"name": "tool_calls_before_named_artifact", "value": 6, "threshold": 3},
        {"name": "no_progress_on_named_artifact", "value": true, "artifact": "README.md:line_12"}
      ],
      "alternatives": [
        {"type": "misalignment", "weight": 0.31}
      ]
    },
    "repair_directive": {
      "class": "reorient",
      "instruction": "The user's request was a 1-line typo fix in README.md:line_12. Stop the refactor. Restate the user's literal request, then perform only that change.",
      "constraints": [
        "do_not_modify_files_other_than: README.md",
        "max_lines_changed: 2"
      ],
      "preserved_state": {
        "user_goal": "Fix typo on line 12 of README.md",
        "verified_facts": ["repo_root: /path/to/agentos"]
      }
    },
    "session_id": "ses_abc123",
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
    "span_id": "00f067aa0ba902b7",
    "classifier": {
      "id": "ryanhub.breakdown.v01.rules",
      "version": "0.1.0"
    },
    "budget": {
      "remaining": 2,
      "limit": 3
    }
  }
}
```

### 2.2 Field reference

| Field | Type | Required | Description |
|---|---|---|---|
| `breakdown.type` | enum | **yes** | One of `drift \| ambiguity \| dead_loop \| misalignment \| context_collapse \| infrastructure_failure \| tool_error` |
| `breakdown.subtype` | string\|null | optional | When applicable: `dead_loop.in_session`, `dead_loop.cross_session`, `context_collapse.within_conversation`, `context_collapse.substrate_state_loss`, `context_collapse.stale_durable_state`. Null otherwise. |
| `breakdown.detected_at` | RFC3339 string | **yes** | Server-side wall-clock of detection |
| `breakdown.confidence` | float `[0,1]` | recommended | Classifier confidence; default `1.0` if rule-based |
| `breakdown.evidence.summary` | string | **yes** | One-sentence human-readable evidence (≤ 200 chars) |
| `breakdown.evidence.turn_refs` | string[] | recommended | IDs of conversation turns that produced the signal |
| `breakdown.evidence.signals` | object[] | recommended | Machine-readable signal records: `{name, value, threshold?, ...}` |
| `breakdown.evidence.alternatives` | object[] | optional | Other types considered, with weights |
| `breakdown.repair_directive.class` | enum | **yes for cognitive types**; null for substrate types | One of `reorient \| clarify \| break_loop \| realign \| reground \| custom` |
| `breakdown.repair_directive.instruction` | string | **yes for cognitive types** | Human-readable instruction (≤ 2000 chars) |
| `breakdown.repair_directive.constraints` | string[] | optional | Machine-checkable post-conditions the orchestrator MAY enforce |
| `breakdown.repair_directive.preserved_state` | object | recommended | Canonical state to re-ground the agent on |
| `breakdown.session_id` | string | **yes** | Stable session identifier; joins to GenAI conventions |
| `breakdown.trace_id` | hex string | **yes** | W3C trace-id (16 bytes hex) |
| `breakdown.span_id` | hex string | **yes** | W3C span-id of the `breakdown.detect` span |
| `breakdown.classifier.id` | string | recommended | Classifier identifier (URN-shaped) |
| `breakdown.classifier.version` | string | recommended | SemVer of the classifier |
| `breakdown.budget.remaining` | int | **yes** | Remaining repair turns for this session (cognitive only; substrate budgets are separate) |
| `breakdown.budget.limit` | int | recommended | Configured budget (default 3) |

### 2.3 Minimum viable payload

For a v0.1-conformant detector emitting a *cognitive* breakdown, this is the MVP — anything less is not a valid breakdown event:

```json
{
  "breakdown": {
    "type": "<one of: drift, ambiguity, dead_loop, misalignment, context_collapse>",
    "detected_at": "<RFC3339>",
    "evidence": {"summary": "<≤200 chars>"},
    "repair_directive": {
      "class": "<one of: reorient, clarify, break_loop, realign, reground, custom>",
      "instruction": "<≤2000 chars>"
    },
    "session_id": "<string>",
    "trace_id": "<hex>",
    "span_id": "<hex>",
    "budget": {"remaining": <int>}
  }
}
```

For *substrate* breakdowns (`infrastructure_failure`, `tool_error`), `repair_directive` is `null` and `budget.remaining` is omitted (substrate failures have their own retry budget at the orchestrator):

```json
{
  "breakdown": {
    "type": "<infrastructure_failure | tool_error>",
    "detected_at": "<RFC3339>",
    "evidence": {"summary": "<≤200 chars>"},
    "repair_directive": null,
    "session_id": "<string>",
    "trace_id": "<hex>",
    "span_id": "<hex>"
  }
}
```

### 2.4 Repair directive classes

| Class | When | Mechanism |
|---|---|---|
| `reorient` | `drift` | Restate the user goal verbatim; ask the agent to re-derive next step from goal, not from current trajectory. |
| `clarify` | `ambiguity` | Surface the resolving question to the user (or escalation target). MUST pause forward progress until resolved. |
| `break_loop` | `dead_loop.in_session` | Forbid the offending action class for *N* turns; require the agent to enumerate ≥ 2 alternative paths before retrying. |
| `realign` | `misalignment` | Surface the proxy metric vs. user-stated criteria; require the agent to re-derive what "good" means. |
| `reground` | `context_collapse` | Re-inject canonical state and require the plan to be re-derived from that state. |
| `custom` | escape hatch | Caller-supplied. The instruction string MUST stand alone without a class hint. |

For `dead_loop.cross_session`, NO repair directive is emitted — the orchestrator enforces a back-pressure gate at dispatch (§4.4). For `infrastructure_failure` and `tool_error`, NO repair directive is emitted — the orchestrator routes to substrate fix (§4.4).

### 2.5 Repair lifecycle (cognitive only)

A cognitive repair flows through four states, each emitting a span (see §3):

```
detected → dispatched → applied → verified
                            ↓
                          failed (terminal)
```

- `detected` — classifier emitted the event.
- `dispatched` — orchestrator has injected the repair turn.
- `applied` — agent has produced ≥ 1 turn after the injection.
- `verified` — follow-up classification on post-repair turns reports no recurrence of the same breakdown type for ≥ *V* turns (default `V = 2`).
- `failed` — verification did not occur within timeout, OR the same breakdown re-fired immediately, OR budget was exhausted.

For substrate breakdowns the lifecycle is different: `detected → halted → fixed → resumed | terminated`. See §4.4.

## 3. W3C-Trace-Compatible Attribute Schema

The Protocol layers over [OpenTelemetry GenAI semantic conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/) and [W3C Trace Context](https://www.w3.org/TR/trace-context/). All attributes use the `breakdown.*` namespace to avoid collision with `gen_ai.*`.

### 3.1 Span types

| Span name | Kind | Parent | Description |
|---|---|---|---|
| `breakdown.detect` | INTERNAL | the agent turn span where the breakdown was identified (cognitive) OR the orchestrator dispatch span (substrate, cross_session) | Emitted by the classifier. Carries all `breakdown.*` evidence attributes. Emitted for ALL types — cognitive AND substrate. |
| `breakdown.repair` | INTERNAL | `breakdown.detect` | Emitted by the orchestrator when a repair turn is injected. **Cognitive types only.** |
| `breakdown.verify` | INTERNAL | `breakdown.repair` | Emitted by the verifier checking whether the repair succeeded. **Cognitive types only.** |
| `breakdown.substrate_action` | INTERNAL | `breakdown.detect` | Emitted by the orchestrator when a substrate fix is attempted. **Substrate types only** (`infrastructure_failure`, `tool_error`, `dead_loop.cross_session`). |

All four spans share the same `trace_id` as the underlying agent session and link to the agent's turn span via parent-span-id.

### 3.2 Span attributes

#### Common (all spans)

| Attribute | Type | Required | Notes |
|---|---|---|---|
| `breakdown.type` | string | **yes** | Enum of 7 categories |
| `breakdown.subtype` | string | optional | Sub-type when applicable (§2.2) |
| `breakdown.session_id` | string | **yes** | Joins with `gen_ai.conversation.id` if present |
| `breakdown.classifier.id` | string | recommended | Classifier identifier |
| `breakdown.classifier.version` | string | recommended | Classifier SemVer |

#### `breakdown.detect`

| Attribute | Type | Required | Notes |
|---|---|---|---|
| `breakdown.confidence` | double | recommended | `[0.0, 1.0]` |
| `breakdown.evidence.summary` | string | **yes** | ≤ 200 chars |
| `breakdown.evidence.signal_count` | int | recommended | Length of `signals[]` |
| `breakdown.evidence.turn_refs` | string[] | recommended | OTel array attribute encoding |
| `breakdown.evidence.alternatives` | string[] | optional | Encoded as `"<type>:<weight>"` strings |
| `breakdown.layer` | string | **yes** | `cognitive` \| `substrate` (drives downstream routing) |

Signal records (each signal): use indexed attribute names per OTel conventions:
- `breakdown.evidence.signals.<i>.name`
- `breakdown.evidence.signals.<i>.value`
- `breakdown.evidence.signals.<i>.threshold` (optional)

#### `breakdown.repair` (cognitive only)

| Attribute | Type | Required | Notes |
|---|---|---|---|
| `breakdown.repair.class` | string | **yes** | Enum of 6 directive classes |
| `breakdown.repair.instruction` | string | **yes** | ≤ 2000 chars; may be truncated in trace export |
| `breakdown.repair.constraint_count` | int | optional | Length of `constraints[]` |
| `breakdown.repair.preserved_state.keys` | string[] | recommended | Top-level keys (values stay out of trace for size) |
| `breakdown.budget.remaining` | int | **yes** | Decremented when repair is dispatched |
| `breakdown.budget.limit` | int | recommended | |
| `breakdown.repair.state` | string | **yes** | Enum: `dispatched \| applied \| failed`. Use span events for transitions (§3.3). |

#### `breakdown.verify` (cognitive only)

| Attribute | Type | Required | Notes |
|---|---|---|---|
| `breakdown.verify.outcome` | string | **yes** | Enum: `verified \| failed \| timeout` |
| `breakdown.verify.observed_turns` | int | **yes** | Number of post-repair turns inspected |
| `breakdown.verify.recurrence_type` | string | optional | If `failed`, the type that re-fired |

#### `breakdown.substrate_action` (substrate only)

| Attribute | Type | Required | Notes |
|---|---|---|---|
| `breakdown.substrate.action` | string | **yes** | Enum: `halt \| refresh_credential \| reset_env \| skip_tool \| backpressure_gate \| terminate` |
| `breakdown.substrate.outcome` | string | **yes** | Enum: `resumed \| escalated \| terminated` |
| `breakdown.substrate.retry_count` | int | recommended | Times this substrate fix has been attempted in this session |

### 3.3 Span events (lifecycle transitions)

Lifecycle transitions are emitted as span events on `breakdown.repair` (cognitive) or `breakdown.substrate_action` (substrate):

**Cognitive (`breakdown.repair`):**
- Event `breakdown.repair.dispatched` — when the repair turn is injected.
- Event `breakdown.repair.applied` — when the agent's post-injection turn arrives.
- Event `breakdown.repair.failed` — when repair times out, recurs, or budget exhausted.

**Substrate (`breakdown.substrate_action`):**
- Event `breakdown.substrate.halted` — when the agent is paused.
- Event `breakdown.substrate.fix_attempted` — when the orchestrator attempts a substrate fix.
- Event `breakdown.substrate.resumed` — when the agent is resumed after fix.
- Event `breakdown.substrate.escalated` — when fix failed and human/operator notification was emitted.

Each event carries its own timestamp; consumers SHOULD prefer events for ordering.

### 3.4 Propagation across handoffs

#### MCP (agent ↔ tool)

When a cognitive repair is in flight (`detected` or `dispatched` but not yet `verified`), tool calls invoked in that window MUST include the following in the MCP request `_meta` field (per MCP spec for arbitrary metadata):

```json
{
  "_meta": {
    "ryanhub.breakdown": {
      "session_id": "ses_abc123",
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "in_flight_type": "drift",
      "repair_state": "dispatched"
    }
  }
}
```

The tool server MAY use this to:
- Tag its own emitted spans with `breakdown.contributed_evidence` if it observes signals consistent with the in-flight breakdown.
- Refuse a no-op call (e.g., the same write the agent just attempted) and return a structured `dead_loop_suspected` error to the agent.

The tool server MUST NOT rely on this metadata — it is informational only. Tools that ignore the field remain v0.1-conformant.

For substrate breakdowns, MCP propagation is OPTIONAL and only used when a tool is the proximate cause (`tool_error`).

#### A2A (agent ↔ agent)

When agent A hands a task to agent B, the task message MUST include a `breakdown.history` field summarizing recent breakdowns (last 5 within session, both cognitive AND substrate):

```json
{
  "breakdown.history": [
    {
      "type": "context_collapse",
      "subtype": "substrate_state_loss",
      "detected_at": "2026-05-03T14:18:00Z",
      "repair_state": "verified",
      "session_id": "ses_abc123"
    },
    {
      "type": "infrastructure_failure",
      "detected_at": "2026-05-03T14:14:00Z",
      "substrate_outcome": "resumed",
      "session_id": "ses_abc123"
    }
  ]
}
```

This lets agent B:
- Avoid re-triggering a just-resolved breakdown (`verified` history items are warning, not error).
- Escalate if the same breakdown type re-fires after a recent `verified` repair.
- Decide whether to retry actions that previously hit substrate failures.

#### W3C trace context

Standard `traceparent` and `tracestate` headers carry trace-id across MCP/A2A boundaries. Breakdown attributes are span-local; cross-system join is via trace-id.

## 4. Orchestrator Contract

This section is normative for orchestrator implementations.

### 4.1 Required behaviors

The orchestrator MUST:

1. **Receive** detect events (in-process, OTLP, or implementation-defined transport).
2. **Validate** the payload against §2.1 (reject events missing required fields).
3. **Route by layer** (`breakdown.layer`): cognitive → §4.2 repair-turn path; substrate → §4.4 substrate-fix path.
4. **Decide** whether to act on the event, considering per-session budget, per-classifier rate limits, and caller-configured policy.
5. **Act**: inject repair turn (cognitive) OR halt + substrate fix (substrate).
6. **Emit** the appropriate span(s) and lifecycle events from §3.
7. **Verify** (recommended for cognitive) by inspecting subsequent turns and emitting `breakdown.verify`.

### 4.2 Cognitive path: repair budget and back-pressure

Per CTO's RYA-745 condition: orchestrators MUST enforce back-pressure to prevent classifier-false-positive repair storms.

**Per-session budget.** Default `3` repair turns per session, configurable. When exhausted:
- `ambiguity` exhausted → escalate to user with all accumulated evidence.
- `dead_loop.in_session` exhausted → terminate the session and surface to operator.
- All other cognitive types exhausted → emit `breakdown.repair_budget_exceeded` span; default policy is terminate + operator notification.

**Per-classifier rate limit.** At most `1` `breakdown.detect` per `(session_id, type)` per `60s` window. A classifier emitting more frequently SHOULD be coalesced (orchestrator drops duplicates and emits a `breakdown.detect.suppressed` span event).

**Repair-after-repair gating.** A repair MUST complete (`applied` OR `failed`) before another repair of the *same* `type` can be dispatched on the same session.

### 4.3 What the orchestrator MUST NOT do

- MUST NOT inject more than one repair turn for a single `breakdown.detect` event.
- MUST NOT inject a repair turn for substrate breakdowns (`infrastructure_failure`, `tool_error`, `dead_loop.cross_session`).
- MUST NOT treat exception-style errors as breakdowns (fail-closed: if `gen_ai.error.type` is set on the parent span, suppress breakdown classification for that turn).
- MUST NOT silently drop a detect event without emitting a `breakdown.detect.suppressed` span event.

### 4.4 Substrate path: halt + fix + resume (load-bearing)

Substrate breakdowns (`infrastructure_failure`, `tool_error`, `dead_loop.cross_session`) route through a fundamentally different repair path. This separation is the load-bearing edit from RYA-770 — without it, a classifier that mis-routes substrate failures into the cognitive path produces repair-turn storms.

The orchestrator MUST:

1. **Halt** the agent (or the dispatcher, for `dead_loop.cross_session`) on detect. NO repair-turn is injected.
2. **Attempt a substrate fix** appropriate to the breakdown type:
   - `infrastructure_failure`: refresh credentials / set missing env var / wait on rate-limit / restart subsystem.
   - `tool_error`: skip the offending tool, mark it suspect, OR surface a structured warning to the agent.
   - `dead_loop.cross_session`: enforce a back-pressure gate at dispatch (deduplicate, cool down, OR terminate the loop entirely).
3. **Per-substrate-type retry budget.** Default `2` substrate-fix attempts per session per type. When exhausted: escalate to operator. This budget is SEPARATE from the cognitive repair budget.
4. **Resume the agent** (or restart the dispatcher) after a successful substrate fix. The agent's pre-halt state is preserved; no repair-turn is injected.
5. **Emit** `breakdown.substrate_action` spans and lifecycle events per §3.3.

**Do not negotiate with the agent about substrate failures.** A repair-turn that says "your tool is broken, please work around it" is exactly the failure mode RYA-770 identified — the agent will produce a coherent-looking response that does nothing useful, and the orchestrator will burn its repair budget on a problem the agent cannot solve.

### 4.5 Multi-detection windowing

If multiple detect events arrive for the same session in a `5s` window:
- Substrate signals pre-empt cognitive (substrate is the proximate cause; resolve substrate first).
- Within the same layer, the highest-confidence signal wins; others are suppressed (`breakdown.detect.suppressed`).

## 5. Detector Contract

The Protocol does not specify a classifier algorithm. v0.1-conformant detectors MAY be:

- **Rules-based** — pattern matching on tool-call repetition, scope inflation, env-var presence, etc. Strong fit for substrate signals.
- **LLM-judge** — a second-pass model evaluates the conversation against the cognitive taxonomy.
- **ML model** — a fine-tuned classifier (out of scope for v0.1; the reference library will ship rules + LLM-judge only).
- **Hybrid** — rules for cheap signals (substrate + dead_loop), LLM-judge for ambiguous cognitive cases.

Detectors MUST:
- Emit one `breakdown.detect` span per detection.
- Populate all required attributes from §3.2.
- Set `breakdown.layer` to `cognitive` or `substrate` correctly (drives orchestrator routing).
- Provide `confidence` if their method supports it (rule-based detectors MAY emit `1.0`).
- Apply the §1.8 tie-break order when multiple types have evidence.

Detectors SHOULD:
- Emit `evidence.signals` for any quantitative signal that contributed to the decision.
- Suppress detection for turns where `gen_ai.error.type` is set (§1.9).

## 6. Conformance Levels

| Level | Requirements |
|---|---|
| **Cognitive-detector-conformant** | Emits `breakdown.detect` spans for cognitive types with all required attributes. |
| **Substrate-detector-conformant** | Emits `breakdown.detect` spans for substrate types with all required attributes. |
| **Detector-conformant** | Both of the above. |
| **Cognitive-orchestrator-conformant** | Receives cognitive detect events, injects repair turns matching §2.1, emits `breakdown.repair` spans, enforces budget. |
| **Substrate-orchestrator-conformant** | Receives substrate detect events, halts agent / dispatcher, attempts substrate fix, emits `breakdown.substrate_action` spans, enforces substrate retry budget. Does NOT inject repair turns. |
| **Orchestrator-conformant** | Both of the above. |
| **Verifier-conformant** | Emits `breakdown.verify` spans tied to repair spans (cognitive only). |
| **Full v0.1** | Detector-conformant + Orchestrator-conformant. Verifier is recommended. |

A v0.1-conformant *system* requires at least one detector and one orchestrator covering BOTH layers (cognitive AND substrate). A system that only handles cognitive is not v0.1-conformant — it will repair-turn-storm on the 32% of incidents that are substrate.

## 8. Training data status & known limits

**ConvFail labeled corpus does NOT yet exist.** RYA-562 is the decision brief approving the ConvFail benchmark; RYA-568 is the AskLess theorem. v0.1 commits to **AgentOS retrospective corpus only** for taxonomy validation and reference-detector training. The corpus is 104 incidents over 30 days, validated under RYA-770.

**Per-class corpus sufficiency for classifier training:**

| Category | n in 30-day corpus | Verdict |
|----------|---|---------|
| `context_collapse` | 22 | OK floor |
| `infrastructure_failure` | 23 | OK floor |
| `misalignment` | 17 | Marginal |
| `drift` | 14 | Marginal |
| `dead_loop` | 12 | Below recommended |
| `tool_error` | 10 | Below recommended |
| `ambiguity` | 6 | **Insufficient — needs ≥ 20** |

The reference TypeScript library (`@ryanhub/breakdown-protocol`, planned under RYA-722) MUST treat the rules-based detector as authoritative for `infrastructure_failure`, `tool_error`, and `dead_loop` (all are observable from logs). The LLM-judge detector is the only viable path for `ambiguity` until corpus expands.

**Known limits of v0.1:**

1. **Cross-session breakdown linkage.** A user's *next* session repeating the same breakdown is signal — but cross-session join (beyond `dead_loop.cross_session`) is out of scope for v0.1.
2. **Classifier confidence calibration.** `[0,1]` is generic; ConvFail data may suggest a calibrated scale per category. Defer to v0.2.
3. **Ambiguity escalation policy.** `clarify` directives need a target (user vs. supervising agent vs. queue). v0.1 makes this orchestrator-policy; v0.2 may standardize.
4. **`over_compliance` / `policy_violation`.** Not a v0.1 category. Adjacent to misalignment but driven by missing rule-application. 0 incidents in current corpus; covered by human-in-loop review path.
5. **AgentOS-specific bias.** The corpus comes entirely from one organization. v0.2 work will require an adapter-validated cross-org sample to confirm the cognitive/substrate split holds at 68%/32% in other agent stacks.
